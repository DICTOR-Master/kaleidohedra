# Run audit: how our computational tests fail, and what would have caught each failure before or early (10 Nov 2026)

Internal study (DICTO: "do we need an audit on how to run tests by Fable analyzing all our failed data?"). Read-only: nothing was launched or changed; only this file was written. Paths and machine names appear here because the report is internal; none of it is for publication.

## Conclusion

Yes, the audit was needed, and the record answers it clearly. Across the ledger, open-work, the study READMEs and the logs on the compute machine, at least 95 run failures of twelve kinds are on record since 11 Oct 2026; the three biggest kinds are **time caps hit with nothing to show** (at least 20), **empty or silent logs** (at least 17 zero-byte logs, output buffered and lost at the kill), and **tooling or environment faults** (at least 12: self-matching pkill/pgrep, nested ssh quoting, a guard file that was empty, a wrong-folder run, Python 3.14 multiprocessing). Almost every failure of the first two kinds was predictable from a five-minute pilot or a growth estimate, and the guards built so far (dbbjob.sh, dbbcheck, runjob.py, the pre-commit hook, the ledger) act **after** the run ends or at commit time; nothing today checks the plan **before** launch, nothing checks that the ledger already settled the question (the k = 32 Santaló run of 10 Nov repeated a level the ledger had marked "no more float levels (memory)" the day before), nothing checks that output is unbuffered, and nothing demands a positive and a negative control before the real cases start. The watcher side is now mostly covered (dbbjob.sh waits, dbbcheck.sh projects the finish); the gaps are at launch, and two of the guards have already drifted (orphans.sh no longer recognises dbbjob.sh's new launch line; the installed pre-commit hook differs from tools/pre-commit). The proposals below are ranked by how many past failures each would have caught; the top three (a pre-flight gate, forced unbuffered output, a control gate) cover about 60 of the 95.

## Pre-flight checklist (answer yes to every line before launch; a "no" is a stop)

1. Is the ledger digest checked and no SETTLED / "never retry" / "no more" entry covers this question and method?
2. Is there a written plan line: stages, size per stage from a pilot, cap per stage, action on each outcome and on overrun?
3. Did a pilot of 5 minutes or less finish on the smallest size, and is the cap set from its measured rate (not a habit value)?
4. Is the count of objects bounded by a stated rule (window, radius, level), never open-ended (dense grids, growing queues)?
5. Is memory estimated from known growth (faces x1.3/level, box = n^6 points) and below `free -g` available, with a per-job ceiling set?
6. Will a positive control with a known answer run first and must it pass before the real cases start?
7. Will a negative control (known UNSAT / known non-fill / wrong offset) run first and must it fail?
8. Does the script print PROGRESS with a FIXED denominator and a BEST value, flushed (python -u or PYTHONUNBUFFERED=1)?
9. Does the script write partial results to disk as it goes and end with a FINAL line that is earned by its own check (ok / FAIL / TIMEOUT)?
10. Is the command shipped as a file through dbbjob.sh with a run_in_background waiter (no raw nohup, no time promise without it)?
11. Do waits and kills use PIDs (kill -0, wait), never pgrep -f / pkill -f on a string?
12. Are the data folder and output path created and tested by the pilot from the script's own folder (runjob.py or an equivalent cd)?

## Guard proposals, ranked by past failures each would have caught

1. **Pre-flight gate in dbbjob.sh** (would have caught about 30: types 1, 2, 6, part of 12). Mechanism: dbbjob.sh refuses to launch unless ~/dbb-logs/NAME.plan exists with lines `estimate_items`, `estimate_mem_gb`, `pilot_rate`, `cap_from_pilot`, `controls`, `bound`; a small preflight.sh compares estimate_mem_gb with `free -g` available minus 10 GB and the cap with pilot_rate x estimate_items, and prints the likely failure modes; a missing or failing plan prints the checklist above and exits 2. The plan file is kept beside the log as the record.
2. **Unbuffered output and early-silence check** (about 20: type 3, part of 1). Mechanism: dbbjob.sh exports PYTHONUNBUFFERED=1 and runs the .cmd under `stdbuf -oL -eL`; dbbcheck_remote.sh flags any job whose log is still 0 bytes 3 minutes after start ("SILENT START: output buffered or crashed before printing") and any job with no PROGRESS line after 10 minutes (already there). This also catches empty-log crashes before the cap.
3. **Control gate** (about 10: type 7, part of 6). Mechanism: dbbjob.sh gets `--control 'cmd' --expect 'TEXT'` (and `--negative 'cmd' --expect 'TEXT'`); it runs the control(s) first under a 5-minute cap, greps the expected line, and launches the real command only on success; a failing control writes the alert "CONTROL FAILED: method or window wrong" instead of starting the run. Today's hidden-space window would have stopped at this gate automatically.
4. **Ledger match at launch** (at least 3 confirmed, likely more: type 12). Mechanism: preflight.sh takes the plan's `question` and `method` keywords and greps ~/k-research/papers/dicto-concordance/ledger-digest.txt for a line with status SETTLED, METHOD-FAILED or a retry rule containing "never" / "no more" / "only with"; a hit prints the entry and requires `--override "reason"`, which is written into the plan and the next ledger entry.
5. **Plateau and open-ended detector** (at least 16: the 9 star runs, the 7 SAT enumerations). Mechanism: jobs print `PROGRESS <fraction> <done>/<total>` and `BEST <value>`; dbbcheck_remote.sh flags "PLATEAU: best unchanged 15 min" and "OPEN-ENDED: total grew by more than 20 % since the last check" (sat-control today: 21,002 -> 22,020 seen within 30 s). Either flag is an instruction to stop and change the method, not to wait for the cap.
6. **Guard regression for ~/dicto-alerts** (type 9 guard rot: empty dbbcheck.sh 11-09, vacuous self-test 11-10, stale orphans.sh regex found today, hook drift found today). Mechanism: ~/dicto-alerts/guard_regress.sh, run by show.sh once a day: (a) launches a 10-second job with a command containing quotes, `;` and `$` and asserts the log holds the expected text; (b) launches a deliberately failing job and asserts an alert file appears; (c) runs orphans.sh and dbbcheck_remote.sh against a live dbbjob job and asserts neither flags it; (d) diffs the installed pre-commit hook against tools/pre-commit (plus the machine_guard line) and warns on drift; (e) warns on any .pid without a .cap. Fix now: orphans.sh regex -> `timeout [0-9.]+h bash (-c|.*dbb-logs/)`.
7. **Per-job memory ceiling** (type 2 collateral, type 11: Singular 40 GB, 385 MB free). Mechanism: dbbjob.sh wraps the command with `systemd-run --user --scope -p MemoryMax=<estimate x 1.5>G` (or `ulimit -v`) from the plan; dbbcheck_remote.sh warns at 80 % of the ceiling ("MEMORY: on course to be killed") so the run can be stopped and split rather than killed at the end.
8. **Earned FINAL line, stricter** (type 10). Mechanism: pre-commit and runjob.py also reject a FINAL ok printed inside a `try/except` that swallows all exceptions or after a loop with no assertion; dbbjob.sh distinguishes `FINAL ok` (result) from `FINAL none: <reason>` (ran fine, no result), so "spacing too small" stops being an OK; the ledger entry is written from that line.
9. **Numerics calibration** (type 8). Mechanism: every interval or exact tool starts with `calibrate()`: an enclosure of 1/3 and of √5 must contain the true value with positive width (outward rounding), a known positive case must pass the screen and a known negative must fail; a failed calibration prints FINAL FAIL before any real case runs (the float Dehn screen of 5 Nov would have stopped here).
10. **Study-close sweep** (type 11, type 5). Mechanism: tools/close_study.py NAME lists every dbb job whose .cmd mentions the study folder, offers to kill them by PID, and writes the ledger entry; show.sh warns when a study README gains a "CLOSED"/"SETTLED" line while a job of that study is still running.

Already in place since 8-10 Nov and worth keeping as is: dbbjob.sh (alert on anything but FINAL ok; command as a file; .cap), dbbcheck.sh STALLED projection, runjob.py, the pre-commit crash-text block, the 20-minute attention check (recreate every session), followups.list.
